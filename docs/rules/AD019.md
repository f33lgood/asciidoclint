# AD019 - content-after-include

Tags: core, structure, includes
Severity: warning
Fixability: no.
Fix helper: Insert a blank line after the include directive or ensure the included file ends with a blank line.

Necessity: Include expansion happens before rendering. Text placed directly after an include can visually attach to the included content unless a clear section or block boundary separates it.


Text should not be attached directly after whole-file include directives when
the included file does not provide its own trailing blank line.

Bad:

```adoc
include::chapter.adoc[]
This paragraph attaches unexpectedly.
```

Good:

```adoc
include::chapter.adoc[]

== Next Section

This paragraph is separate.
```

Rendering rationale: include expansion happens before rendering. Content placed
directly after an include can attach visually to included content unless a clear
section or block boundary separates it. Fragment includes with `tag`, `tags`, or
`lines` are exempt because they are commonly used to include a piece of a block
inside surrounding content.

Asciidoctor documentation recommends empty lines around include directives when
including AsciiDoc content to avoid unexpected parsing after expansion. For
example, if `chapter.adoc` ends with `included paragraph` and the parent has
`include::chapter.adoc[]` immediately followed by `== Next`, Asciidoctor can
render `== Next` as paragraph text instead of a section title.

Implementation note: AD019 is a source-scanner rule backed by the include graph.
It checks whole-file local includes. It reports only when the include target is
resolved, the included file does not end with a blank line, and the next parent
line is nonblank content that is not an obvious safe boundary such as a block
delimiter, anchor, attribute entry, or block attribute. Fragment includes using
`tag`, `tags`, or `lines` are intentionally exempt.

Limitation: AD019 does not fully simulate Asciidoctor preprocessing. It does not
parse the included file to prove the final expanded block type, and it does not
try to validate intentional inline reuse. The rule is a conservative warning for
the common whole-file include boundary hazard.
